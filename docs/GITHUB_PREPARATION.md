# Подготовка к GitHub

Рекомендуемое название приложения — **IT Support Workbench**, репозитория — **`it-support-workbench`**. Оно совпадает с `package.json` и описывает рабочую среду для диагностики, практики и развития в IT-поддержке. Переименовывать папку `it_homelab` для этого не требуется.

## Первый коммит

```text
feat: добавить IT Support Workbench для диагностики и обучения
```

Это первая публикация всего готового приложения `0.3.0`, поэтому название описывает результат целиком.

## Description

```text
Local-first IT support workbench for Windows diagnostics, guided troubleshooting, network tools, and hands-on learning. No backend or cloud processing.
```

## Topics

Добавляйте каждое слово как отдельный topic:

```text
it-support troubleshooting network-diagnostics windows networking dns subnetting vue typescript vite local-first offline-first learning-tool developer-tools
```

## Что уже подготовлено

- README с запуском, возможностями, скриншотами и ограничениями; исходное ТЗ, техническая документация и MIT License.
- `.gitignore` исключает зависимости, сборку, результаты тестирования, `.env`, журналы, приватные ключи и служебные файлы macOS. Исходники, fixtures, скриншоты, `package-lock.json` и конфигурация GitHub включаются.
- `.gitattributes` нормализует текст в LF и сохраняет изображения как бинарные файлы.
- CI выполняет форматирование, lint, strict typecheck, unit-тесты с покрытием, сборку и e2e в Chromium, Firefox и WebKit. Параллельные устаревшие запуски одной ветки отменяются.
- GitHub Actions закреплены полными commit SHA; checkout не сохраняет токен в Git-конфигурации. Dependabot готов предлагать еженедельные обновления npm и Actions, без автоматического слияния.
- Шаблоны ошибок, предложений и pull request помогают описывать воспроизводимые изменения с синтетическими данными.
- Публикация Pages запускается вручную только из `main`, требует успешного CI для того же SHA и повторно проверяет приложение. Сам push исходников сайт не публикует.

## Порядок первой выкладки

1. Создайте пустой репозиторий `it-support-workbench` с нужной видимостью. README, LICENSE и `.gitignore` уже находятся в проекте. Заполните Description и Topics из этого документа.
2. Инициализируйте локальный Git с основной веткой `main`, если он ещё не создан. Выполните предварительный просмотр списка файлов:

   ```bash
   git init -b main
   git add --dry-run .
   git status --short --untracked-files=all
   ```

   Убедитесь, что вы добавляете исходники, документацию и синтетические примеры. Персональные отчёты приложения храните за пределами репозитория: произвольные `.txt`, `.md` и `.json` автоматически приватными не считаются. Секреты не включайте через `git add -f`.

3. Создайте первый коммит с предложенным названием, подключите адрес своего нового репозитория и выполните push самостоятельно. Remote, имя владельца и URL заранее не зашиты в проект.
4. Дождитесь workflow **CI**. Если он завершился ошибкой, исправьте причину до публикации сайта. Результат локальной проверки описан в [VALIDATION.md](VALIDATION.md); удалённый Linux CI нужно подтвердить отдельно.
5. При желании опубликовать приложение настройте Settings → Pages → Source: **GitHub Actions**, затем вручную запустите **Deploy GitHub Pages** для `main`. Этот шаг нужен только для сайта; хранение проекта в GitHub готово отдельно.
6. Для публичного проекта включите private vulnerability reporting в настройках безопасности, чтобы механизм из [SECURITY.md](../SECURITY.md) был доступен. После появления URL сайта можно добавить его в поле Website репозитория.

## Почему после первой выкладки появились четыре ветки

`main` содержит опубликованную версию приложения. Остальные три ветки созданы Dependabot по конфигурации `.github/dependabot.yml`: это предложения обновить TypeScript, `actions/deploy-pages` и `actions/upload-pages-artifact`. Для каждой ветки бот открыл Pull Request — запрос на включение обновления в `main`. Пока PR не объединён, основная версия приложения не меняется. Эти ветки не являются результатом ошибки push или падения CI.

После принятия обновления через **Merge** временную ветку можно удалить кнопкой **Delete branch**. Для автоматической очистки после слияния включите **Settings → General → Pull Requests → Automatically delete head branches**. Если обновление не подходит, закройте PR; оставшуюся ветку можно удалить отдельно. [Официальная инструкция GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-the-automatic-deletion-of-branches).

`main` остаётся основной веткой. При последующих обновлениях Dependabot может создавать новые ветки и PR; еженедельное расписание уже задано, но первая проверка запускается при включении конфигурации. Удаление ветки после слияния сохраняет изменения, уже включённые в `main`, и историю PR. Изменять эти настройки и принимать обновления нужно отдельно; подготовка проекта не включает автоматическое слияние или удаление веток.

Проверки 09.10.2026 не обнаружили известных уязвимостей через `npm audit` или распространённых шаблонов секретов в публикуемом наборе файлов. Это результаты конкретного аудита, а не гарантия отсутствия любых уязвимостей или конфиденциальных данных. Архивы пользовательских кейсов и реальные корпоративные логи в проект не добавлялись.

Репозиторий в рабочей папке, remote, коммит, push, CI-run и сайт при подготовке не создавались. Никакие личные токены для текущих workflows не требуются: используется стандартный `GITHUB_TOKEN`.

Настройки сверены с официальной документацией: [закрепление Actions по SHA](https://docs.github.com/en/actions/reference/security/secure-use), [фильтрация CI по commit SHA](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-workflow), [GitHub CLI API](https://cli.github.com/manual/gh_api).
