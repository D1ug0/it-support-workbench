# Следующие улучшения обучения

Предложения после работы 11.10.2026. Это будущие этапы, не реализованные этим изменением. Уже есть карта навыков, повторение вопросов, профессиональные инциденты, отчёты, авторские материалы и настоящий Linux/HTTP-шаблон. Ниже предлагаются конкретные расширения этих возможностей.

## 1. Короткая тренировка конкретной ошибки — первый рекомендуемый этап

**Проблема:** общая рекомендация выбирает тему, но свободный текст ошибки не всегда превращается в точное упражнение. Повторение того же вопроса может проверять запоминание ответа.

**Первый объём:** DNS, три ошибки: путаница прямого запроса и кэша, смешение NXDOMAIN и отказа DNS-сервера, необоснованная смена DNS. Назначать короткое занятие на 5–10 минут: объяснение → новая ситуация → выбор доказательства → проверка другим вопросом позже. Использовать совместимые ID ошибок/компетенций; прежние текстовые ошибки продолжать читать.

**Готово, когда:** ученик видит причину рекомендации; исправление подтверждается новым контекстом, а не тем же вопросом; правильное решение убирает активную рекомендацию, сохраняя историю ошибки; результат не становится автоматическим подтверждением всего навыка.

## 2. Расследование с неизвестной причиной

**Проблема:** название лаборатории часто раскрывает неисправность, а три фиксированных варианта профессионального случая можно запомнить.

**Первый объём:** одна заявка «Не открывается учебный портал», несколько воспроизводимых причин с одинаковым симптомом: кэш, DNS, маршрут, отказ зависимости. Вход показывает заявку и масштаб, а не техническое название неисправности. Причина определяется исследованием; seed сохраняется в конкретной попытке, перезагрузка не меняет условия. Режим использовать отдельно от существующих известных лабораторий.

**Готово, когда:** разные причины требуют разных доказательств; перебор исправлений без основания не даёт полноценного результата; после решения показаны причина, последствия изменений и свежая проверка пользовательского запроса; старые оценки не пересчитываются.

## 3. Структурированная таблица гипотез и доказательств

**Проблема:** заметки и ссылки на шаги есть, но ученику приходится вручную сопоставлять предположение, наблюдение и границу вывода.

**Первый объём:** для одного профессионального инцидента добавить строки «Гипотеза → Проверка → Наблюдение → Подтверждает/опровергает/недостаточно данных → Следующий шаг». Доказательство выбирается из фактической истории попытки. Отмечать устаревшую проверку после изменения состояния и противоречащие наблюдения.

**Готово, когда:** строка ведёт к исходному результату; предположение нельзя выдать за подтверждённый факт без проверки; отчёт экспортирует эту структуру; самостоятельные заметки и текущие черновики сохраняются совместимо.

## 4. Разбор объяснения по рубрике

**Проблема:** автоматическая оценка процесса не устанавливает качество свободного объяснения. Полезно показать отдельно, что проверил движок, а что требует разбора человеком.

**Первый объём:** один инцидент и пять критериев: масштаб, обоснование гипотезы, минимальность изменения, актуальность проверки, условия отката/эскалации. После попытки ученик сопоставляет свой отчёт с критериями и двумя контрастными примерами. Наставник может добавить отдельный комментарий и оценку объяснения, явно обозначенную ручной проверкой.

**Готово, когда:** автоматические баллы и ручной разбор видны отдельно; комментарий не переписывает исходный отчёт; эталон не открывается до попытки; шаблон допускает несколько обоснованных путей решения. Первый этап может работать локально, без нового сервера или внешнего AI.

## 5. Реальные Windows-примеры и обозначение подтверждённой совместимости

**Открытая граница:** `src/fixtures/real/manifest.json` пуст. Синтетические результаты и успешный Linux/HTTP-стенд не подтверждают Windows CMD/PowerShell.

**Первый объём при наличии собственной Windows VM:** одна команда `ipconfig /all`, минимальный рабочий и известный проблемный вывод, версии ОС/локали, ручное обезличивание и независимый expected JSON. Затем `nslookup` и `Test-NetConnection`. Использовать готовые [сборщик и строгий manifest](REAL_FIXTURES.md).

**Готово, когда:** реальные пары проходят `npm run test:fixtures:real`; исходный смысл и переносы сохранены; в матрице указаны только фактически проверенные версии/локали. Не создавать реальные captures из синтетических fixtures.

## Дополнительные небольшие улучшения

- Единый экран прогресса: показывать связь двух существующих журналов и различие между «знакомство», «самостоятельное решение», «проверка после перерыва» и «отчёт стенда».
- Перенести отображение событий в отдельный компонент, когда появится фильтрация/поиск по истории; разделять терминальную страницу по рабочим блокам по мере их изменения, сохраняя сценарии.
- Проверить screen reader и мобильную клавиатуру на целевых устройствах. Автоматический Axe этого не заменяет.

Рекомендуемый порядок: короткая тренировка ошибки → одна заявка с неизвестной причиной → таблица доказательств → рубрика объяснения. Windows-проверки выполнять при доступном собственном окружении. Каждый этап заканчивать одним рабочим сценарием и целевыми проверками, прежде чем расширять каталог.
