# Архитектурный аудит и рефакторинг — 12.10.2026

## Результат

Проект постепенно приведён к Feature-Based Architecture + Clean Architecture Light. Основной рефакторинг выполнен в `workshop`, где действительно смешивались интерфейс, правила, реактивное состояние и IndexedDB. Стек и продуктовые сценарии сохранены. Текущее устройство и правила импорта: [ARCHITECTURE.md](ARCHITECTURE.md). Численные результаты и список прежних браузерных сбоев: [evidence JSON](audits/2026-10-12-architecture-evidence.json).

## Исходные проблемы

В исходном HEAD у workshop было 80 файлов, из них 72 непосредственно в одной папке. `useWorkshopStore` совмещал очередь и согласие с описанием таблиц, CAS-транзакциями, сохранением материалов и историей отчётов. Несколько панелей работали с Dexie-таблицами напрямую. Professional-фасад реэкспортировал и домен, и хранилище: импорт схемы мог подгрузить IndexedDB. Learning и simulator зависели от внутренних технических файлов workshop. Глобальный поиск в `shared` импортировал features.

Большие Vue-файлы содержали одновременно формы, маршруты, сохранение, отмену запоздалых результатов и отображение. Чистые парсеры и обезличивание находились в `infrastructure`; Worker transport — в `application`. Публичные входы и направления импортов не проверялись автоматически. Циклов статических runtime-импортов исходный граф не содержал; проблема заключалась в ответственности и границах, а не в уже существовавшем цикле.

Первый unit-прогон: **645 passed, 6 failed, 1 skipped**. В рабочем дереве уже были изменения подготовки окружения — Windows-инструкция и `.ts`-расширения импортов companion. Они сохранены.

## Выполненные этапы

1. **Выделение операций и порта.** Обновление события, проверки теории и assessment вынесено в чистый `domain/progressCommands.ts`. `application/workshopRepository.ts` описывает необходимые store операции. Реальные транзакции, CAS и история отчёта перенесены в адаптер. Проверены сериализация отделённых снимков, отказ записи, сохранение RAM и opt-in через подставной порт и существующие регрессии.
2. **Организация workshop.** Код распределён по `domain`, `application`, `model`, `infrastructure`, `ui`. Панели сгруппированы по обучению, авторству, расследованию, стенду и обмену. Простые тесты находятся рядом с реализацией, многомодульные — в `__tests__`.
3. **Отделение UI и хранилища.** Логика трёх крупных панелей вынесена в composables конкретных сессий. UI вызывает именованные операции репозиториев вместо сырых учебных таблиц. Схема черновика отделена от IndexedDB; professional API экспортирует только домен. Отчёты стенда больше не требуют загрузки полного backup-адаптера.
4. **Общий kernel и адаптеры.** SkillId и совместимость ID попыток имеют общего владельца в `src/domain/learning`. Чистые парсеры/обезличивание перенесены в `src/domain/diagnostics`; Worker — в infrastructure feature анализа. Общая учебная БД вынесена в `src/infrastructure/learning-storage`; learning/simulator больше не импортируют внутренний workshop storage. Общий разбор повреждённых коллекций размещён в shared; поиск перенесён в app.
5. **Публичные входы и проверки.** Доменные и Pinia-входы workshop разделены. Сохранены отдельные async панели. Для всех существующих features объявлены публичные файлы и разрешённые направления; добавлен AST-checker с 15 тестами, включённый в npm-проверки и CI.
6. **Документация и передача разработки.** Обновлены ARCHITECTURE, README, CONTRIBUTING, TESTING и добавлен AGENTS.md. В документации описаны владельцы, репозитории, согласия, CAS, миграции, тесты и ограничения checker.

Число строк уменьшилось благодаря отделению ответственности; логика сессий сохранена в именованных composables. Это не удаление возможностей. В корне workshop теперь один публичный `index.ts`; реализации находятся в слоях. Крупные каталоги не разрезались искусственно по числу строк.

## Данные и совместимость

Исходник определения общей БД совпадает с исходным HEAD после нормализации переносов строк. Сохранены имя `it-support-workbench-workshop`, версия 4, история версий 1–4, 11 таблиц и индексы. Новая миграция данных не требуется.

Не менялись форматы записей, backup v1/v2, progress/checkpoint, ключи opt-in, ID store, материал/отчёт tokens, CAS, пределы коллекций и правила атомарного restore. Учебный бюджет — 12 MiB, транспортный лимит backup — 16 MiB. Проблемные исходные записи остаются доступными для восстановления. Сохранены явное сохранение, RAM без согласия, офлайн allowlist и опциональность companion/AI.

## Оставшиеся ограничения

1. **Старый E2E-набор требует отдельного обновления.** 47 прежних сбоев воспроизводятся до рефакторинга: старые заголовки/подписи, адреса и ожидания текущего учебного интерфейса. Набор не считается прошедшим. Список точных сценариев сохранён в evidence JSON; UI ради старых selectors не менялся.
2. **Полный трёхдвижковый контроль не зелёный.** Firefox из установленного Playwright-комплекта имеет известный отказ Windows SideBySide/mozglue, обнаруженный при подготовке окружения; итоговая попытка запуска также завершилась `spawn UNKNOWN`. Полный WebKit-набор не повторялся; новые сценарии данных в нём проходят. Перед выпуском нужны рабочий Firefox и актуальные E2E для всех движков.
3. **Границы остальных features имеют разную глубину.** Небольшие возможности сохраняют именованные файлы вместо пяти папок. Крупные `TerminalPage`, network engine и статические каталоги остаются следующими кандидатами на разделение при росте; их логика уже имеет чистые функции. Техническая композиция обычного store по-прежнему связывает конкретный локальный адаптер.
4. **Checker не доказывает runtime-безопасность всего кода.** Он проверяет разрешимые файловые зависимости и статические циклы и отдельно проходит lazy-зависимости чистых слоёв. Косвенные вызовы, новое динамическое разрешение путей и aliases требуют расширения правил и тестов. Связи learning/workshop/terminal на уровне продукта остаются явными.
5. **Операционные проверки вне объёма.** Remote CI/публикация, реальные Windows captures, Linux Docker-стенд и ручной screen-reader не запускались. Новые аккаунты, внешняя инфраструктура и AI-запросы не создавались.

Следующий приоритет — актуализировать старые E2E по текущему пользовательскому пути и восстановить Firefox runner. Затем при появлении новых требований можно выделить отдельные model-сессии для авторских коллекций/портфолио и части terminal UI, сохраняя существующие порты, очередь и контракт данных.

Итоговый dev-сервер запущен на <http://127.0.0.1:5173/>. Обучение, терминал и настройки дополнительно открыты в Chromium из исходников без ошибок JavaScript. Форматирование всего проекта и `git diff --check` проходят.
